# 《乃木坂女学院》单集开发工具流与编剧纪律

> 状态：**项目级固定工作流 / Writers' Room Operating System。**
>
> 适用于后续所有 EP 的开发、审查、锁定与定稿。除非某集存在明确、可说明的特殊原因，不随意跳步，不把后段工具提前拿来掩盖前段问题。
>
> 本工作流必须与 `docs/writing/writers-room-collaboration-principles.md` 同时使用：本文件规定**按什么顺序工作**，后者规定**我们怎样一起创作**。如果流程执行方式会把编剧排除在人物、关系、关键场景、喜剧、结尾等创作判断之外，说明执行方式本身已经违反项目原则。
>
> 目标不是把每一集写成同一种故事，而是用同一套方法保证：现实成立、制度成立、人物不被剧情工具化、观众能跟上、对白关系正确、镜头可执行、情绪不被作者解释掉，同时保留逐场阶段继续长出更好戏的空间。

---

# 一、总纲

本文件只规定单集开发顺序与 Gate。编剧室怎样共同创作、哪些内容可以落盘、怎样使用 Git，分别由：

- `writers-room-operating-card.md`；
- `writers-room-collaboration-principles.md`；
- `episode-artifact-naming-standard.md`；
- `github-usage-standard.md`

负责，不在这里重复展开。

标准判断顺序是：

> **现实 / 制度成立 → 人物能够自然行动 → 故事与场景成立 → 戏剧效果。**

前一层出现硬伤，不使用后一层的漂亮对白、镜头或情绪替它找借口。

同时保留两条创作护栏：

> **摄影机不是世界运行的原因。**
>
> **前期结构负责搭脚手架；逐场阶段仍然是正式创作。**

完整风格与表达判断进入 `dialogue-principles.md`、`non-explanation-principle.md`、`audience-perspective-review.md` 和视觉节奏文件，不把本工作流扩写成第二份风格圣经。

---

# 二、运行方式

单集在四种状态间移动：

> `ROOM OPEN → DEVELOPMENT → FINALIZATION → POST-FINAL`

- `ROOM OPEN`：正式 STEP 前的发散与感觉对齐；
- `DEVELOPMENT`：STEP 0–15；
- `FINALIZATION`：STEP 16–17；
- `POST-FINAL`：交棒后的非 canon 聊天与本集硬伤维护。

所有步骤继续遵守：

- 观众必须知道故事，不必知道我们的感悟；
- 角色可以说明场内真实需要的事实、任务、作品与困难；
- 对白、画面和声音都不得替观众总结意义；
- 人物特质来自她多做了什么，不来自周围人突然失去常识；
- 人物卡与行为引擎优先于剧情机关；
- 群像不要求人人在高潮露脸；
- 生活感不需要剧情功能证明，也不允许成为数量配额；
- 一次成功的形式、动作或结尾不自动成为后续公式。

这些是判断边界，不是待逐项表演给主创看的 checklist。

# 四、标准工具流｜STEP 0—17

正式工作流开始前，必须先完成 `writers-room-collaboration-principles.md` 规定的 **Room Opening**。它不是 STEP，不建立 episode 文件；只有主创明确表示感觉已经对齐、可以进入工作状态，才进入 STEP 0。

为避免每个节点拥有同样的仪式重量，执行时区分两类：

| 类型 | 节点 | 默认方式 |
|---|---|---|
| 共同创作 | Room Opening；STEP 0、2、3、5、7、9、12、15、16；任何人物、结构、场景意义或 canon 取舍 | Assistant 主动发散 / 起草，主创参与判断，明确确认后推进 |
| Assistant 先行检查 | STEP 1、4、6、8、10、11、13、14、17 的资料、压力测试与机械审计部分 | Assistant 完整执行并报告；无创作取舍可简短通过，发现 RED 或需修改作品时回编剧室 |

分类不改变 STEP 顺序，也不授权 Assistant 自行锁定创作决定。它只避免主创为没有发现的机械检查逐项按“下一步”。

进入 STEP 0 前，Assistant 先用极短的“对齐回声”复述：共同兴趣、仍开放的可能和已经知道不能做什么。该回声不是 Episode Brief，主创确认没有误读后才正式开工。

## STEP 0｜本集任务定义

在想桥段以前，先回答：

1. 表层发生什么？
2. 这一集真正改变什么？
3. 谁是 M / S / L / R？
4. 哪些人物弧可以推进？
5. 哪些人物弧本集**禁止提前消费**？
6. 本集结束时，观众比开头多知道什么 / 多感觉到什么？
7. 哪些东西明确留给后续 EP？

### 特殊形式集追加：Form Contract

如果本集使用严格实时、一镜到底、Bottle Episode、限定空间、平行实时、特殊视角等形式，STEP 0 必须另外定义：

- **Diegetic Clock｜世界时间**：故事世界实际经过多少时间；
- **Camera Clock｜摄影机时间**：摄影机连续经历多少时间；
- **Target Runtime｜成片时间**：观众最终观看的大约时长；
- **不可作弊原则**：该形式禁止用什么手段偷掉成本或掩盖结构问题。

三种时间不能默认等同。

特殊形式只服务本集命题，不自动推广成全剧统一形式。

### Gate 0

如果一句话说不清“这一集为什么存在”，先不进入 Beat Sheet。

特殊形式集若无法说清 Form Contract，也不进入下一步。

## STEP 1｜现实 / 制度压力测试

所有涉及以下内容的桥段，默认先查现实：

- 日本学校制度；
- 典礼 / 课程 / 学生会；
- 称呼与礼仪；
- 通学；
- 家庭与升学；
- 医疗；
- 建筑；
- 消防、疏散、耐震、无障碍；
- 行政流程；
- 公共系统；
- 电子设备 / 校规；
- 其他会随现实制度变化的事项。

优先采用当代日本官方学校、自治体、运营主体、公共机构、规则与可靠的一手信息。影视作品只能作为表现参考，不能作为现实证明。

研究结果应尽量区分：

- 常规做法；
- 少见但专业上成立；
- 需要特殊条件；
- 明显不成立；
- 剧作许可，但需要制作端帮助成立。

研究目标是排除现实或行业的一票否决，不是证明选定方案最常见。确认“少见但成立”且必要条件可满足后，可以停止继续证明，把如何让观众接受交回创作与制作。

固定三问：

> **Q1｜如果摄影机今天没来，这所学校本来会怎么做？**
>
> **Q2｜既然现实本来会这样发生，我们的人物会比别人多注意什么、多做什么、做出什么选择？**
>
> **Q3｜摄影机应该在哪里，才能让观众看见这个差异？**

注意：Q3不能反过来修补Q1、Q2。

### Gate 1

只有当现实流程、权限、信息来源、空间与时间基本成立，才进入人物跑测。

---

## STEP 2｜人物行为引擎跑测

先不给人物“剧情任务”，只把真实事件放进去。

每个关键人物问：

1. 她第一秒把这件事理解成什么问题？
2. 她会先自己处理，还是立即拉别人进来？
3. 她的求助阈值多高？
4. 她如果找人，为什么找这个人而不是另一个？
5. 这是 A 安全区、B 稳定亲近还是 C 摩擦关系？
6. 她会说真实情绪，还是只说事情？
7. 如果这一次违反默认行为顺序，是否意味着人物正在变化？

同时检查相遇来源：

- 被动相遇；
- 制度相遇；
- 生活相遇；
- 主动相遇。

### Gate 2

如果剧情必须先规定“她要这么做”，人物才能走到下一步，先重写条件，不急着重写人物。

---

## STEP 3｜Beat Sheet

Beat Sheet 回答：

> **这集故事为什么成立？**

只处理：

- 主要时间段；
- 核心因果；
- 人物推进级别；
- 情绪换挡；
- 必要伏笔 / 回声；
- 开头、转折与结尾。

不要在 Beat Sheet 阶段提前写满对白和镜头。

权威文件优先为：

`beat-sheet.md`

---

## STEP 4｜Beat Sheet 压力测试

检查：

- 目标时长里装得下吗？
- 是否每条信息都被写成完整场景？
- 是否一个人物被抬成万能中枢？
- 是否小角色因为承担因果而意外获得过大镜头权？
- 是否为了主题提前消费后续人物弧？
- 是否连续几段都在做同一种事？
- 主要冲突来自人物 / 制度 /现实，还是作者强行制造？

核心纪律：

> **不是删信息，而是避免每条信息都拥有自己的完整场景。**

### Gate 4

故事骨架成立后冻结**大型因果结构**。进入 Scene List 后，不因为突然想到一个漂亮小场就随意改骨架；但这不意味着后续场景创作被封死。

---

## STEP 5｜Scene List / Sequence

回答：

> **这些事情实际怎样连续发生？**

检查：

- 场次是否过碎；
- 哪些只是插镜 / montage / 同一连续行动链；
- 人物为什么恰好在这里；
- 空间能否支持动作；
- 信息如何从 A 到 B；
- 人物位置能否自然交叉；
- 哪些因果应发生在其他场景边缘，而不是被单独端上来。

警报句：

> **最大的危险有时不是观众看不懂，而是观众太容易看出编剧正在帮助他们看懂。**

---

## STEP 6｜Scene List 压力测试

逐场问：

- 这真的是一场，还是一个逻辑节点？
- 摄影机是不是为了结构方便把人传送过来？
- 普通学生 / 教师 / 工作人员有没有正常生活？
- 是否出现“某条线亮红 → 专门切过去提醒观众”的荧光笔感？
- 少对白场景仅靠动作，观众能否理解 A 类信息？
- 空间关系是否需要提前建立？

### Gate 6

Scene List 的观看体验应该像连续生活，不像流程图逐项打勾。

---

## STEP 7｜Treatment

Treatment 回答：

> **这东西真的能被演员和摄影机完成吗？**

开始落地：

- 具体动作；
- 谁先到 / 后到；
- 谁站哪里；
- 人群与普通学生；
- 实际空间使用；
- 道具状态；
- 大致对白长度；
- 时间成本；
- 客串权重；
- 声音来源；
- 转场方式。

原则：

> **逻辑重量 ≠ 镜头重量。**

> **一个小角色的逻辑可以比她的戏份大。**

Treatment 开始以后，创作仍然开放。结构层没有提前推演出的更自然动作、空间用法、关系距离可以在这里出现，只要不暗中破坏已锁大型因果。

---

## STEP 8｜Treatment 压力测试

重点检查：

- 现实执行是否真的可拍；
- 动线、时间、人群是否够用；
- 客串是否抢走主角；
- 某机制是否因为镜头过多反而变成观众主动追踪的 B 线；
- 预计时长是否与纸面章节时长一致；
- 专业流程是否被戏剧需求扭曲；
- 哪些“解释”其实应该由动作、空间、声音承担。

### Gate 8

进入 screenplay 前，大型故事、物理机关、人物功能原则上都应该已经稳定。

“稳定”指不再随意重做大型结构，不指后续只能机械翻译 Treatment。

---

## STEP 9｜Screenplay

此阶段主要解决：

- 行为如何落成；
- 对白；
- 停顿；
- 进出场；
- 动作节奏；
- 笑点落点；
- 情绪温度。

这时不应频繁重做大的故事结构。

但必须明确：

> **Screenplay 是第二次正式创作，不是 Beat Sheet 的抄写阶段。**

很多真正属于角色和这所学校的东西，会在具体场景里才出现。只要新发现没有制造硬冲突，就允许它被讨论、吸收和锁定。

对白强制使用：

`docs/writing/dialogue-principles.md`

每一句先问关系，再问字面。

权威文件：

`screenplay.md`

---

## STEP 10｜完整连续性审查

这一遍只查**客观世界是否成立**，不评价感不感人，不评价主题。

检查：

- 时间；
- 地点；
- 人物位置；
- 信息拥有关系；
- 道具 / 设施状态；
- 空间；
- 物理动作；
- 前后因果；
- 失败条件是否真的消失以后才允许方案恢复；
- 路线 / 通勤 / 换场 / 清扫 / 搬运是否现实可完成。

核心问题：

> **如果把这集当成真实发生的一天，它能不能按这个顺序真的发生？**

发现硬伤标记 RED，先修现实，再谈戏。

特殊形式集必须在这里复核 STEP 0 的 Diegetic Clock / Camera Clock / Target Runtime 是否仍然一致。

---

## STEP 11｜观众视角审查

使用：

`docs/writing/audience-perspective-review.md`

暂时忘掉：

- 人物卡；
- 编剧注释；
- 因果模型；
- 创作会议；
- 作者意图；
- 后续还没播出的剧情。

只承认：

- 画面；
- 对白；
- 声音；
- 剪辑顺序；
- 此前正片已经建立的事实。

信息等级：

- **A｜必须明白**；
- **B｜最好能感觉到**；
- **C｜只留潜意识。**

审查等级：

- **GREEN**：足够；
- **YELLOW**：主要依赖拍法 / 视觉关系，需要制作注意；
- **RED**：缺少 A 类信息，必须修。

新增纪律：

> **“观众只看懂了一半”不自动等于 YELLOW。**

只要 A 已经懂、B 已经感觉到，剩下的是 C，那么就是 GREEN；不要为了让观众准确说出人物主题而补解释。

修补不按媒介排高下。先问人物在场内真实会怎样沟通，再确认 A 类信息是否成立，最后删除对白、画面或声音替观众总结意义的部分。

---

## STEP 12｜逐场五层锁定｜同时也是场景创作阶段

从前往后逐场锁。

默认协作方式：

> **Assistant 先写 / 先评 → 编剧纠偏、补完或提出新方向 → 明确确认 → 再 LOCK。**

除非编剧主动要求批量处理，否则默认：

> **一场一锁。**

这一阶段不是单纯验收。很多更好的桥段、动作、对白、喜剧、关系距离与世界规律可以在逐场观看时出现。

每场至少过五层：

### A｜人物行为引擎

- 去掉剧情功能，她还会这样做吗？
- 有没有临时增加技能？
- 有没有为了主演露脸而强行出现？
- 有没有违反默认行为顺序却没有人物变化理由？

### B｜普通人常识保护

- 是否为了突出主角，让普通人不知道她们本来应该知道的常识？
- 是否把一个正常制度写成只有主角理解？
- 是否让熟悉环境的人突然像第一次来？

如果是，优先修主角表现方式。

### C｜日式关系对白

- 关系层级对吗？
- 场合对吗？
- 身份接口对吗？
- 是自然中文，还是翻译腔？
- 有没有把所有角色写成同一种客气短句机器？

### D｜作者解释减法

问：

> **删掉这句话以后，观众仍然知道发生什么吗？**

如果知道，而且感觉更强，删。

### E｜观众视角复核

删除解释以后，A 类信息是否仍然 GREEN？

四层漂亮但 A 类断裂，也不能锁。

### F｜Scene → World Canon Promotion 检查

每场锁前额外问：

> **这里解决的是本场问题，还是暴露了以后所有类似场景都应该遵守的项目级规律？**

如果只是本场：写进 `scene-locks.md`。

如果可泛化：可以提议升级到 World / Series Bible；**必须由编剧明确确认后才能升级 canon**，不能由 Assistant 因为“这个规则很漂亮”自行推广。

### Scene Lock 规则

锁定以后，不因“想到更漂亮的说法”随便重开。

只有发现：

- 连续性硬伤；
- 现实 / 制度硬伤；
- 人物硬伤；
- A 类观众信息 RED；
- 安全 / 制作不可执行；

才重开。

但在 LOCK 之前，场景阶段出现此前没推演到、却明显更准确的创意，不属于违规回退。

---

## STEP 13｜整集节奏 / 重复审查

脱离单场视角，从头到尾连续读完整集。

只查：

- 哪一段明显过长；
- 连续几场是否同质；
- 同一人物动作是否重复；
- 同性质笑点是否连续；
- 看钟 / 看表 / 点头 / 叹气 / 望窗外等动作是否过密；
- 情绪是否一直只升不降；
- 沉重场景后是否有生活回来；
- 喜剧是否打断真实动作；
- 信息是否重复；
- 群像是否变成轮流点名露脸；
- 气口是否仍有可感受内容。

目标：

> **不是每分钟都有剧情，而是观众愿意继续和这些人待在这里。**

---

## STEP 14｜表演 / 镜头 / 空间 / 声音审查

这一关放在后面，避免提前用导演技巧替剧本补洞。

重点问：

- 哪句对白应该改成停顿？
- 哪个心理应该交给动作 / 眼神？
- 哪个地方应该让人走掉，不再多说一句？
- 哪个呼应只需要动作出现？
- 重要空间轴是否可追踪？
- 关键视线是否物理成立？
- 反应镜头有没有真正新信息？
- 声音能否承担换挡？
- 长镜头内部有没有持续变化？
- 某些 B / C 信息是否应交给导演，而不是继续写台词？

硬原则：

> **不要拍“这一刻很重要”；要把空间、动作、视线和声音拍清楚，让观众自己觉得它重要。**

如果视觉方案和已锁定 A 类因果冲突，先修视觉方案，不默认新增解释对白。

---

## STEP 15｜最终无工具通读

这是防止 QA 系统把作品修成机器的一关。

暂时关掉：

- checklist；
- 人物卡；
- RED / YELLOW 标记；
- 结构图；
- 因果模型；
- 创作会议说明。

只把它当一集电视剧看。

问：

- 好看吗？
- 人活着吗？
- 有没有“编剧非常努力”的痕迹？
- 会不会太正确？
- 有没有地方明明通过所有检查，却没有生命？
- 有没有一段让我只想继续看，而不是继续分析？
- 结尾的情绪属于人物此刻，还是作者提前替以后伤感？

工具服务作品，不反过来统治作品。

---

## STEP 16｜FINAL

FINAL 的定义不是“永远不能碰”。

它意味着：

> **停止偏好型无限润色。**

### FINAL READY CHECK｜请求编剧确认前必须机械通过

在说“可以 FINAL”以前，先核对：

- `episode-artifact-naming-standard.md` 规定的标准产出物已齐全；
- 所有已完成 Gate 的文件头状态一致；
- `scene-locks.md` 全场 `LOCKED / CLOSED`；
- `screenplay.md` 没有残留已经废弃的旧设定；
- `final-read.md` 已 `PASS / CLOSED`；
- episode 目录没有与当前事实冲突的旧 `DRAFT / 暂名 / IN PROGRESS` 权威状态；
- `FINAL.md` 即将引用的文件都真实存在。

> **Scene Locks 全部 CLOSED 不等于 Episode FINAL。**

未通过 READY CHECK，不得告诉编剧“这一集已经完成”或擅自进入下一集。

通过 READY CHECK 后，再由编剧明确确认 FINAL。

允许 FINAL 后重开的理由：

- 连续性硬伤；
- 新确认的现实 / 制度错误；
- 安全问题；
- 制作不可执行；
- A 类观众信息 RED；
- 明显人物硬伤。

不允许重开的理由：

- 今天想到一句更漂亮的台词；
- 想再给喜欢的角色多一个反应；
- 想让一个已经成立的 callback 更显眼；
- “这一场还能更感人”。

Final 时原则上只需要：

- 当前权威正文已是最终真相；
- `screenplay.md` 文件头标记 `FINAL / LOCKED`；
- 明确 final commit；
- `FINAL.md` 只做状态索引 / 制作说明，不复制正文。

---

## STEP 17｜Canon Propagation｜定稿后全库同步

一集 FINAL 不等于项目已经知道它 FINAL。

定稿后必须搜索全库，检查本集新事实是否改变：

- Series Bible；
- 人物卡；
- 行为引擎；
- 关系网；
- Season Structure；
- Character Pressure Matrix；
- Callbacks；
- World；
- Open Decisions；
- README / 项目状态；
- 后续 EP 已经引用的前提；
- 其他长期权威文档。

传播必须同时检查三类变化：

> **Add + Remove + Reclassify**

### Add

加入正片新成立的长期事实。

### Remove

删除项目仍然相信、但已经被正片推翻的旧计划、旧路线与旧未来。

### Reclassify

调整事实等级，例如：

- 正式安排 → 未经确认的风声；
- S → L / R；
- 明确人物前置 → 只保留校园口碑前置。

原则：

> **一个场景定稿，不等于项目定稿。只有所有依赖这个事实的权威文档都知道它已经改变，这个事实才真正成为 canon。**

Canon Propagation 完成后，必须再做一次 **Link / Status Audit**：

- `FINAL.md` 引用文件真实存在；
- FINAL commit 正确；
- Canon 状态正确；
- README / 下一开发对象正确；
- 没有悬空链接；
- 没有项目级权威继续宣称旧状态。

完成后，本集才真正结束。

随后执行“一集一任编剧”交棒：

- 本任 Assistant 编剧不进入下一集的正式编写；
- 可以完成继任信、《编剧室采访》及全剧范围的自由发散；
- 对未来集数的发散不建立 episode 产出物，不推进 Gate，不 LOCK，不自动成为 canon 或待办；
- 下一集由下一任 Assistant 编剧读取权威状态后，从自己的正式开发起点开始。

如果 FINAL 后发现本集符合 STEP 16 所列重开条件，本任编剧仍负责维护本集；这不构成进入下一集。

> **前任可以留下火花，不能给继任者留下债务。**

---

# 五、回退规则

流程允许回退，但必须知道为什么回退。

回退分为两类：

- **创作层回退**：回到较早 STEP 重新处理人物、结构、现实或场景；
- **仓库层回退**：修正已经进入远端的文件状态或提交。

仓库层回退不得把 Git 时间点直接等同于作品目标。执行前必须：

1. 用自然语言定义希望恢复的事实；
2. 明确允许变化与禁止变化的文件范围；
3. 生成候选文件树，与当前状态及已知正确状态比较；
4. 向主创展示文件级差异并取得明确确认。

> **回退恢复的是指定事实，不是某个过去时刻。不得仅凭提交顺序推断哪些工作“不该发生”。**

- STEP 10 连续性发现现实硬伤 → 回 STEP 1 / 5 / 7，不在对白层补洞。
- STEP 11 观众 A 类 RED → 回 STEP 5 / 7 / 9，补可见桥梁。
- STEP 12 人物硬伤 → 回 STEP 2，重新跑行为引擎。
- STEP 12 场景阶段自然长出更准确的局部创意 → 在对应层级修改，不自动重开整集。
- STEP 12 发现可泛化世界规律 → 编剧确认后再提升到 World / Series Bible。
- STEP 13 节奏重复 → 优先合并 / 删除 / 降镜头权，不先增加新剧情。
- STEP 14 空间拍不懂 → 先修调度 / 轴线；如果物理本身不成立，再回 STEP 1 / 7。
- STEP 15 “都对但不好看” → 找真正缺失的欲望、关系或生活，不机械增加金句和冲突。

回退不是失败；**不知道自己为什么回退**才会制造无限修订。

# 六、Git 文档纪律

## 1. 文件回答“现在是什么”，Git 回答“以前是什么”

同一职能优先只保留一个稳定文件名，例如：

- `beat-sheet.md`
- `scene-list.md`
- `treatment.md`
- `screenplay.md`
- `continuity-review.md`
- `audience-review.md`
- `scene-locks.md`

正常修订直接修改并 commit，不用 `v0.5 / v0.6 / revision-v1.2` 堆叠版本历史。

## 2. 重要共识必须进入 Git

出现以下任一情况就应该落盘：

- 双方明确认可；
- 成为后续因果前提；
- 进入逐场审查；
- 标记 LOCKED / FINAL；
- 未来需要精确回溯。

脑暴不必全部提交；稳定事实不能只活在聊天里。

特别是新的协作方法、风格纪律、世界规律一旦确认，不得只留在聊天总结中；应进入 Writing / Series Bible / World 对应权威文件，使新对话可以恢复。

## 3. 新文件只用于新的信息职能

适合新文件：

- screenplay 与 continuity review；
- 世界观与人物卡；
- 具有长期研究价值的压力测试；
- 两套确实需要同时比较的互斥路线；
- 项目级协作原则等真正新的长期信息职能。

不适合新文件：

- 改几句对白；
- 修一个时间点；
- 锁定范围向后推进；
- 母稿吸收新修订；
- 因为怕找不到旧版而复制全文。

## 4. 旧项目文件不盲删

EP05 等早期开发已产生大量版本文件。

整理时先确认：

- 当前权威文本；
- 交叉引用；
- 哪些压力测试具有独立价值。

再删除失效重复版本，由 Git 历史保留旧状态。

# 七、每集完成条件

一集进入 FINAL 前，应满足：

- 本集任务与 M/S/L/R 分配清楚；
- 特殊形式集已明确 Diegetic / Camera / Runtime 与不可作弊原则；
- 关键现实 / 制度问题已经查证；
- 人物行为来自既有引擎，而不是剧情临时改人格；
- Beat Sheet、Scene List、Treatment、Screenplay 的当前权威状态一致；
- 逐场创作已经由编剧实际参与，而不是 Assistant 自动跑完后一次性交付验收；
- 所有 Scene Locks 已经得到明确确认；
- 完整连续性无硬伤；
- A 类观众信息全部 GREEN；
- YELLOW 已明确是可接受拍法依赖或已有视觉硬要求；
- 无关键 RED；
- 普通人常识没有被牺牲给主角光环；
- 对白符合日本关系逻辑；
- 作者解释已尽量删除；
- 不存在明显重复人物动作 / 功能性露脸；
- 整集节奏连续观看通过；
- 表演 / 镜头 / 空间 / 声音审查通过；
- 最终无工具通读通过；
- 标准 episode 产出物齐全且状态一致；
- FINAL READY CHECK 通过；
- 编剧明确确认 FINAL；
- 权威文件已提交 Git；
- Canon Propagation 完成 Add / Remove / Reclassify；
- Link / Status Audit 通过。

# 八、桌面版核心检查句

遇到犹豫，按顺序问：

> **如果摄影机今天没来，这件事现实里本来怎么发生？**
>
> **制度允许谁做什么、知道什么？**
>
> **这个人自己真的会这么做吗？**
>
> **她为什么会在这里、为什么找这个人？**
>
> **有没有为了主角成立，让普通人突然失去常识？**
>
> **第一次看的观众知道足以跟上故事的那一层吗？**
>
> **日本人在这个关系里会这么说吗？**
>
> **这句是在传达故事，还是替观众总结感悟？**
>
> **能不能删掉一句，让感觉反而更强？**
>
> **镜头是在拍清楚事实，还是在提醒观众“这里很重要”？**
>
> **这个人是本来就要做这件事，还是为了摄影机才做？**
>
> **这场单独很好，但连续看一整集会不会重复？**
>
> **这里刚发现的是本场细节，还是应该提升成项目级规则？**
>
> **所有工具都关掉以后，这仍然是一集好看的电视剧吗？**

---

# 九、新对话 / 上下文恢复

当上下文中断、模型切换或开启新对话时，不要求编剧重新口述整个项目。

默认先读：

1. `docs/writing/README.md`
2. `docs/writing/writers-room-operating-card.md`
3. `docs/writers-room/current-desk.md` 与 README 所示当前项目状态
4. 上一集 `FINAL.md` / `canon-propagation.md`
5. 当前开发集已有文件
6. 与当前集相关的 Series Bible / World / Structure 权威文件
7. 需要判断边界时，再读取本文件或对应完整规范

恢复以后先明确：

- 当前开发对象；
- 当前 Gate；
- 已 LOCK / FINAL 的事实；
- 当前真正未决的创意；
- 哪些下一步必须邀请编剧参与。

不要把记忆当作唯一状态，不要让编剧重复已经落盘的历史。

# 十、最终原则

这套流程不是为了消灭直觉，而是为了保护真正有价值的直觉不被不合理的现实、人物工具化、解释过度和制作漏洞拖垮。

> **先让世界成立。**
>
> **再让人物自己活。**
>
> **再组织成故事。**
>
> **场景里允许它继续长。**
>
> **最后才追求漂亮。**

当作品已经成立，就停止证明它成立。

但在它真正 LOCK 之前，不要因为流程已经往前走，就拒绝一个在具体场景里才刚刚出现、明显更好的东西。

> **Assistant 负责把流程看牢；编剧始终留在“这场戏到底应该怎么活”的房间里。**
