# 《乃木坂女学院》GitHub 使用规范

> 状态：**项目级 LOCKED 标准。**
>
> 本文件规定《乃木坂女学院》编剧室怎样把讨论、锁定、文件状态与 GitHub 历史连接起来。它不要求每一任编剧使用相同客户端，但要求所有人留下同一种可验证状态。
>
> 总纲：**讨论留在编剧室，当前事实写进文件，变化历史交给 Git；锁定只有到达远端才算完成。**

---

# 一、四种状态必须分开

本项目同时存在四种不同事实：

1. **编剧室讨论**：正在尝试、发散、评价与修正的内容；
2. **文件正文**：项目当前认为“现在是什么”；
3. **文件头状态**：该文件当前能否被当作权威引用；
4. **Git 历史**：当前事实怎样从以前的版本变化而来。

因此：

> 一个内容被 commit，不等于它自动 `LOCKED`。

> 一个文件写着 `LOCKED`，但尚未推送远端，也不算完成交接。

只有以下三项同时成立，锁定才真正完成：

- 编剧已经明确确认；
- 权威文件正文与状态已经同步；
- 对应提交已经存在于远端仓库。

GitHub Issue、Pull Request 描述、review comment 和聊天记录都不能代替项目权威文件。它们可以记录工作过程，但不能成为唯一 canon 来源。

---

# 二、草稿确认与写入授权

所有创作性新增或修改，默认先在编剧室展示，再由编剧确认后写入文件。

Assistant 不得采用：

> 自己提出方案 → 自己判断通过 → 自己落盘 → 自己锁定

作为默认工作方式。

编剧室用语与 Git 行为统一如下：

| 编剧表达 | 默认 Git 行为 |
|---|---|
| `写一版看看`、`先显示出来`、`我们先磨` | 只在对话中展示，不落盘 |
| `先过`、`这版可以` | 当前内容获得认可；是否立即发布结合紧邻上下文判断 |
| `锁`、`推进`、`落盘`、`提交`、`推送` | 写入权威文件、更新状态与必要传播、commit 并 push |
| `完整推送` | 检查所有已经确认但尚未发布的内容，完成传播、commit 与 push |
| `继续` | 若紧接当前版本的明确通过，则锁定当前单元并进入下一项；否则只继续讨论或工作 |

如果表达与上下文仍然存在会改变作品的实质歧义，不自行选择不可逆方向；先保持草稿状态并确认。

`LOCK` 的完成条件不是“已经修改文件”，也不是“已经本地 commit”，而是：

> **远端已经拥有该原子提交。**

# 三、两条发布路径

## 1. 日常编剧路径｜确认后直接进入 `main`

以下工作默认在编剧室确认后直接提交并推送 `main`：

- 场景锁定；
- 世界观锁定；
- 人物设定锁定；
- 已确认文本修订；
- 单集流程节点更新；
- Canon Propagation；
- 普通文档与状态同步。

固定顺序：

> **展示草案 → 讨论 → 编剧明确确认 → 落盘 → 状态 / Canon 传播 → 原子提交 → 立即推送 `main`**

编剧已经在 Writers' Room 完成最终审议时，不为同一决定再建立一个只会重复审议的 PR。

## 2. 结构维护路径｜`agent/*` 分支与 PR

以下工作默认使用独立分支和 PR：

- 大规模文件迁移或重命名；
- 删除大量历史文件；
- GitHub Actions、自动化与仓库配置；
- 脚本、程序或工具修改；
- 尚未决定是否采用的实验；
- 需要并排审查的大范围重构；
- 编剧明确要求使用 PR 的工作。

分支统一命名为：

```text
agent/<short-kebab-topic>
```

例如：

```text
agent/ep05-artifact-migration
agent/github-workflow-cleanup
```

PR 默认先作为 Draft。合并后，现有 `.github/workflows/agent-branch-lifecycle.yml` 负责为合并提交建立由分支后缀派生的标签，并移除已经合并的远端 `agent/*` 分支。

不得为了保存普通创作草稿建立分支。普通草稿应先留在编剧室；只有真正需要仓库级并排审查的实验才进入 GitHub 分支。

# 四、一锁一提交，一提交一推送

默认原子单位：

> **一个经过确认的创作决定，以及使该决定在全库成立所必需的传播。**

例如，一项旧礼堂空间锁同时修改 World、EP01、EP04、EP05 接口文件，仍然属于一个提交，因为这些文件共同表达同一个决定。

不得：

- 把多个尚未分别确认的创作决定塞入同一提交；
- 把未确认草稿与已锁定内容混在一起；
- 在没有明确原因时把权威文件与必要传播拆成相隔很久的提交；
- 为同一个锁连续制造 `temp → fix → really final`；
- 把已经锁定的内容长期留在本地等待以后批量推送。

每完成一个锁定单元，如一场戏、一幕、一个章节、一项人物 / 世界设定或一个流程节点，必须立即 commit 并 push。

# 五、工作区安全

每次开始工作、准备暂存和提交完成后，都必须检查：

```bash
git status --short
```

固定纪律：

- 任何既有修改默认属于编剧、前任编剧或另一项未完成工作；
- 不得擅自恢复、覆盖、删除或吸收；
- 发现未提交的其他改动时，必须保留原样并向编剧报告；
- 混合工作区不得使用 `git add -A`；
- 不得使用 `git commit -am`；
- 只显式暂存本次锁定涉及的文件；
- 不得使用 `git reset --hard`、强制 checkout 或其他破坏性清理；
- 不得为了让工作区看起来干净而修改与本轮无关的文件；
- 提交后再次确认未相关文件仍保持原样。

如果本轮必须修改一个已经带有他人未提交改动的同一文件，且无法安全区分边界，应停止写入并请求编剧决定，不自行覆盖。

# 六、提交信息

提交信息使用简短、具体的英文祈使句，描述这个提交改变了什么，不描述投入了多少工作。

推荐动词：

- `Lock`
- `Refine`
- `Add`
- `Propagate`
- `Fix`
- `Remove`
- `Finalize`

示例：

```text
Lock old auditorium architecture
Lock EP04 Day 3 referral timing
Refine EP04 Day 3 restraint
Add EP04 development interview
Propagate Hori voice-check lock
Fix EP01 auditorium capacity status
Remove obsolete timing note
Finalize EP04 screenplay
```

禁止使用：

- `temp`；
- `update`；
- `changes`；
- `misc`；
- `final final`；
- 只写文件名；
- 在事实尚未锁定时使用 `Lock`；
- 在单集尚未完成 FINAL readiness 时使用 `Finalize`。

复杂但仍属一个原子决定的提交可以增加简短 body，说明传播范围或硬约束；普通创作锁不需要模板化长说明。

# 七、推送前后校验

## 推送前

必须确认：

- 已检查完整 diff；
- `git diff --check` 通过；
- 没有未确认内容；
- 没有夹带他人或其他任务修改；
- 文件头状态与实际 Gate 一致；
- 必要 Canon 已传播；
- 本次提交能够用一句话准确命名。

## 更新远端

- `main` 只允许 fast-forward 更新；
- 禁止 force push `main`；
- 推送前若远端已经前进，先停止发布并核对新增提交；
- 不得以覆盖远端方式解决分歧；
- 不同环境可以使用本地 Git、GitHub CLI 或 GitHub API，但必须保持相同父提交、相同文件树和相同 fast-forward 结果。

## 推送后

必须确认：

- 远端分支已经指向新提交；
- 远端文件树与本地提交内容一致；
- 本地分支与 `origin/main` 对齐；
- 未相关的未提交文件仍保持原样。

随后向编剧报告：

- 改了什么；
- 文件路径或传播范围；
- commit hash 与标题；
- 当前分支；
- 工作区是否干净；
- 如不干净，剩余修改属于什么范围、是否被本轮触碰。

# 八、FINAL 的 Git 规则

单集 FINAL 至少区分两个事实：

## 1. 正片完成

提交示例：

```text
Finalize EP04 screenplay
```

该提交使 `screenplay.md` 与相关审查文件进入正确的 `FINAL / LOCKED`、`PASS / CLOSED` 状态。

## 2. FINAL Canon 传播

后续提交示例：

```text
Propagate EP04 final canon
```

该提交在 `FINAL.md` 中记录准确的 FINAL commit，并完成：

- `canon-propagation.md`；
- README 当前状态；
- World / Series Bible / Structure 同步；
- Link / Status Audit。

这样避免让 `FINAL.md` 在同一个尚未产生的提交里记录自己的未知 SHA。

普通场景锁不创建 tag。是否为每集 FINAL 建立固定标签，需要另行形成项目级决定，不由单任编剧临时发明。

# 九、错误与历史修正

如果错误尚未推送，可以在不触碰他人修改的前提下修正本轮内容并重新校验。

如果错误已经进入远端 `main`：

- 不改写公开历史；
- 不 force push；
- 小范围错误使用明确的 `Fix ...` 修正提交；
- 整个提交需要撤销时使用正式 revert；
- Canon 被修正时，同步处理仍然存活的旧 Canon；
- 向编剧说明错误、影响范围与修正提交。

目标不是让历史看起来从未犯错，而是让继任者能够准确理解错误怎样被发现和纠正。

---

# 十、交接与恢复

每一轮工作结束或发生长时间上下文中断时，至少留下：

- 当前分支；
- 本地与远端是否同步；
- 最新提交 SHA；
- 当前工作流 STEP / Gate；
- 本轮锁定内容；
- 尚未锁定内容；
- 工作区是否存在未提交文件；
- 未提交文件属于谁或哪项工作，是否被本轮触碰。

新任编剧恢复工作时，不得只读 Git log 猜测当前事实，也不得只依赖聊天记忆。必须先读 Writing System、当前权威文件及其状态，再使用 Git 理解变化历史。

不同编剧可以使用不同 Git 工具，但必须留下同一种可验证状态：

> **编剧确认清楚，文件状态清楚，提交边界清楚，远端状态清楚，未完成工作也清楚。**
