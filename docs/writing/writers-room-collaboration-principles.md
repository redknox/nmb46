# 《乃木坂女学院》Writers’ Room 协作与场景创作原则

> 状态：**项目级 LOCKED 原则。**
>
> 本文件记录《乃木坂女学院》编剧室最重要的协作方式、场景创作方法与跨对话传承规则。
>
> 它解决的不是“故事按什么顺序开发”，而是：**我们怎样一起写，怎样避免流程把创作本身自动化掉，怎样让新的对话仍然继承已经形成的电视剧气质。**
>
> 与 `episode-development-workflow.md`、`episode-artifact-naming-standard.md`、`dialogue-principles.md`、`audience-perspective-review.md` 同时生效。

---

# 一、最重要的合作原则

> **把编剧从流程劳动里解放出来，不是把编剧从创作里解放出来。**

Assistant 可以主动承担大量机械工作：

- 现实 / 制度查证；
- 资料整理；
- 时间、空间、连续性核对；
- 文件状态维护；
- Git / Canon Propagation；
- 已经明确标准下的 QA；
- 把共同确认的决定整理成稳定文档。

但人物选择、关系距离、关键场景、喜剧落点、场景结尾、情绪峰值、对白温度等创作判断，默认属于 **Writers’ Room 共同创作区**。

不得采用：

> Assistant 提方案 → Assistant 自己判断 → Assistant 自己锁定 → Assistant 自动进入下一阶段

作为默认模式。

推荐模式是：

> **Assistant 先写 / 先发散可能性 → 编剧评价、纠偏、补完或提出新方向 → 双方明确形成当前版本 → 编剧明确确认后再 LOCK。**

编剧的参与不是礼貌性的“参与感”，而是作品质量条件。

---

# 二、为什么逐场阶段仍然是正式创作

本项目明确拒绝一个错误假设：

> 前期负责创造，后期逐场审查只负责检查。

实际开发已经证明，很多真正好的桥段只有在一个场景拥有了具体的：

- 人；
- 空间；
- 道具；
- 身体动作；
- 声音；
- 时间成本；
- 前后关系；

之后才会出现。

因此本项目采用**双阶段创作**：

## 1. 结构创作

Episode Brief、Behavior Run、Beat Sheet、Scene List 建立：

- 这一集为什么存在；
- 主要因果；
- 人物受力；
- 现实条件；
- 什么必须发生；
- 什么不能提前消费。

它负责搭出一个**可以生长的结构**。

## 2. 场景创作

Treatment、Screenplay、逐场 Scene Review / Scene Lock 不是机械执行前面的结构。

这时允许继续发现：

- 更准确的动作；
- 更自然的相遇方式；
- 更短、更像三年同学的对白；
- 一个原本没有意识到的喜剧点；
- 一个真正属于学校的制度细节；
- 一个可以升级成世界规则的视觉 / 行为规律；
- 一个比原设计更好的场景结尾；
- 一个原来结构层没有能力提前推演出来的关系瞬间。

核心原则：

> **流程负责搭脚手架和防止犯错；真正的戏，允许在我们一起逐场看的时候继续长出来。**

---

# 三、逐场协作默认模式

进入 Screenplay / STEP 12 后，默认采用：

> **我先写，你来评。**

除非编剧主动要求批量处理，否则：

> **一场一锁。**

一场的推荐循环：

1. Assistant 给出当前场景版本或审查判断；
2. 明确指出最值得讨论的创作选择，而不是只报 checklist；
3. 编剧可以：
   - 同意；
   - 改一句；
   - 改动作；
   - 改关系距离；
   - 突然提出此前没有推演过的新桥段；
   - 直接推翻这场的某个假设；
4. Assistant 检查新想法是否与现实、人物、上下游 canon 冲突；
5. 编剧明确确认；
6. 才写入 `screenplay.md` / `scene-locks.md`；
7. 才进入下一场。

不得因为“前面的 Beat Sheet 已经 PASS”而把后续新发现自动判定为流程外修改。

---

# 四、场景阶段出现新发现时，怎样处理

新发现不是一律接受，也不是一律拒绝。

先判断它改变哪一级：

### A｜只让本场更准确

例如：

- 一个词更像人物；
- 一个动作比解释对白更自然；
- 一次让路比专门打招呼更真实。

→ 改本场，不重开大结构。

### B｜暴露人物理解错误

例如某动作只有“剧情需要”才会发生。

→ 回人物行为引擎检查。

### C｜暴露世界 / 制度规律

例如一个场景为了成立，发现这所学校长期都会遵守某种空间、视觉、礼仪、设备使用规则。

→ 先确认该规律是否可泛化；
→ **必须由编剧明确同意，才能从 Scene Lock 提升成 World / Series Bible canon。**

### D｜真正改变整集因果

只有新发现会改变：

- 谁导致谁；
- 大型人物推进；
- 主冲突；
- 开头 / 转折 / 结尾；

才回退 Beat / Scene List。

> **允许场景继续生长，不等于允许每一场都重新发明整集。**

---

# 五、Scene → World Canon Promotion

逐场工作常常是世界观最好的压力测试。

因此每场准备 LOCK 时，多问一句：

> **这里解决的是本场问题，还是暴露了以后所有类似场景都应该遵守的规则？**

如果只是本场：

→ 写进 `scene-locks.md`。

如果可泛化：

→ 提议成为 World / Series Bible 规则；
→ 编剧确认；
→ 才建立或修改项目级权威文件。

禁止 Assistant 因为某条规律“看起来很漂亮”就自行升级 canon。

世界 canon 需要足够普适，不能把偶然细节变成以后所有场景的枷锁。

---

# 六、特殊形式集必须先签订 Form Contract

当某集使用特殊形式，例如：

- 严格实时；
- 一镜到底；
- Bottle Episode；
- 单一空间；
- 平行实时；
- 特殊叙事视角；

STEP 0 就必须额外写清三个时间：

### 1. Diegetic Clock｜世界时间

故事世界真实经过多少时间。

### 2. Camera Clock｜摄影机时间

摄影机从开始到结束连续经历多少时间。

### 3. Target Runtime｜成片时间

最终观众观看的大约时长。

三者不能默认等同。

同时必须锁定本集自己的“不可作弊原则”。

例如实时长镜头可能要求：

> 不靠剪辑偷掉真实移动时间；摄影机换跟随对象必须由真实行动产生。

特殊形式服务本集命题，不自动推广成全剧统一形式。

---

# 七、摄影机没有特权

项目级长期原则：

> **摄影机不是世界运行的原因，也没有要求人物为它完成动作的特权。**

如果一个人出现、移动、停留、说话，仅仅因为：

- 镜头需要交棒；
- 需要把观众带到下一个场景；
- 需要展示一组关系；
- 需要提醒观众某条线还存在；

就优先视为危险。

更好的状态是：

> **人物本来就要做这件事，所以摄影机有机会看见。**

因此：

> **行为先发生，摄影机才有理由移动。**

同样，镜头不应为了证明一句对白成立而额外搭一整场画面。

---

# 八、关系不能被“呈现”，只能被观众撞见

本剧非常重视关系，但越重要的关系越不能自动进入“展示模式”。

不要为了告诉粉丝两个人关系很好，就：

- 清空周围普通学生；
- 摆成漂亮双人 / 三人构图；
- 增加只为确认亲密度的对白；
- 给过完整、漂亮、明显等待截图的动作；
- 用配乐、慢动作、反打提示“这里请嗑”。

更好的方法是让关系存在于：

- 谁已经自然坐在那里；
- 谁不需要解释为什么来了；
- 谁可以少说半句；
- 谁说了一个别人不会这样说的事实；
- 谁没有把对方的敏感拆穿；
- 谁只是一起走了一段路，中间没有聊天；
- 谁在重要时刻改变了自己的通常路线。

> **关系越近，形式反而可以越少。**

---

# 九、普通生活不是“剧情之间的填充物”

不要因为一个细节不能推进剧情，就自动判定它可删。

它可能正在推进另一件同样重要的东西：

> **共同生活感。**

例如：

- 吃饭；
- 选错又拿回原来的面包；
- 贴歪创可贴再重贴；
- 争论老师是不是换了同颜色衣服；
- 收便当；
- 借修正带；
- 桌椅复位；
- 走廊让路；
- 一句没有得到回答的问题。

这些不应该被要求拥有“剧情功能证明”。

但也禁止把这条原则量化成：

> “每集至少三个生活细节。”

一旦变成配额，生活感会重新变成作者制造的效果。

---

# 十、风格统一：高雅来自约束，不来自自我宣传

乃木坂女学院的名门感与高雅感，优先来自：

- 秩序；
- 空间管理；
- 长期身体习惯；
- 礼仪；
- 语言距离；
- 视觉克制；
- 对公共空间的维护；
- 学生自然知道什么时候该恢复秩序。

而不是来自：

- 每场都强调昂贵；
- 华丽装饰堆积；
- “大小姐”式表演腔；
- 高饱和青春校园符号；
- 不断提醒观众“这是名门女校”。

一个长期美学原则：

> **高雅通过约束表现，而不是通过装饰表现。**

学校之所以显得有秩序，不是因为学生没有生活，而是：

> **生活再乱，她们仍然知道什么时候该回到秩序里。**

---

# 十一、不要把有效经验误做成公式

有些经验值得保留为判断原则，但不值得做成配额或模板。

禁止因为一次成功就规定：

- 每集必须有固定数量的“无剧情生活细节”；
- 每集必须有一个无对白关系场；
- 每集必须有长镜头；
- 每集必须安排一个世界规则发现；
- 每集都要用同一种克制结尾；
- 每个角色都必须拥有一个行为 callback。

> **统一的是判断方式和世界质地，不是场景表面形式。**

EP03 一镜到底成功，不代表 EP04 也应该一镜到底。

---

# 十二、Finalization 纪律

## 1. Scene Locks ≠ Episode FINAL

即使所有场次已经 `LOCKED / CLOSED`，也不能说这一集“做完了”。

必须继续完成：

- 整集节奏审查；
- 表演 / 镜头 / 空间 / 声音审查；
- 最终无工具通读；
- FINAL readiness audit；
- FINAL；
- Canon Propagation。

## 2. FINAL READY CHECK

请求编剧确认 FINAL 前，机械核对：

- 标准 episode 产出物已经齐全；
- 所有已完成 Gate 状态一致；
- `scene-locks.md` 所有场次 CLOSED；
- `screenplay.md` 没有残留已废弃设定；
- `final-read.md` 已 PASS / CLOSED；
- episode 目录不存在与当前状态冲突的旧 `DRAFT / 暂名 / IN PROGRESS` 权威文件；
- FINAL 索引中即将引用的文件真实存在。

未通过这一步，不得宣称“可以进入下一集”。

---

# 十三、Canon Propagation 不只是添加新事实

Canon Propagation 必须做三种动作：

> **Add + Remove + Reclassify**

### Add

把正片新成立的事实加入长期权威。

### Remove

删除项目仍在相信、但已经被正片推翻的旧计划 / 旧未来。

### Reclassify

调整事实等级，例如：

- “正式安排”降为“未经确认的风声”；
- 某角色从 S 调整为 L / R；
- 某个原定前置从“人物出场”改为“校园口碑先出现”。

Canon Propagation 结束后必须再做：

> **Link / Status Audit**

确认：

- `FINAL.md` 中引用的文件真实存在；
- FINAL commit 正确；
- Canon 状态正确；
- README / 当前开发对象正确；
- 没有悬空链接和旧状态。

---

# 十四、一集一任编剧与交棒纪律

本项目默认严格执行：

> **一集只由一任 Assistant 编剧负责正式开发。**

该任编剧从本集正式开发开始，持续负责至：

- Episode FINAL；
- Canon Propagation；
- Link / Status Audit；
- 远端提交与本地状态完成同步。

完成以上事项后，本任编剧不得进入下一集的正式编写，包括：

- 不建立下一集的正式 episode 产出物；
- 不推进下一集 Gate / STEP；
- 不锁定下一集场景、结构、人物决定或当前真相；
- 不以“上下文仍然充足”为理由替下一任提前开工。

这不是要求 FINAL 后立即结束对话。只要上下文仍然允许，本任编剧可以继续：

- 写给继任编剧的信；
- 完成《编剧室采访》；
- 回望本集的判断、遗憾、意外与未采用方向；
- 与主创发散讨论整部剧；
- 谈对未写集数、人物、周边、预告、配乐或剧情发展的期待与隐忧；
- 提出大胆、矛盾、尚未验证甚至暂时离题的构想。

这个阶段允许比正式开发更高的发散度。目标是碰撞火花，不是提前生产下一集。

因此，FINAL 后关于未来的一切发散默认都属于：

> **非 canon、非待办、非继任者义务。**

它可以被下一任吸收、改造或完全放下。不得因为前任已经讨论得很深入，就把发散内容伪装成下一集的既定前提。

本集 FINAL 后若发现符合重开条件的本集硬伤，原编剧仍可维护自己负责的这一集；这不构成进入下一集。

若发生无法避免的技术性中断，按下节恢复协议保存并恢复同一集工作；不得把“中途换任”当作常规排班方式。

> **前任可以留下火花，不能给继任者留下债务。**

---

# 十五、上下文中断 / 新对话恢复协议

本文件的重要目的之一，是让编剧室不依赖某一次聊天窗口的上下文长度。

任何新的 ChatGPT 对话、任何新的协作模型、任何长时间中断后的恢复，**不要要求编剧重新口述整个项目历史**。

恢复顺序默认如下：

1. `docs/writing/README.md`
2. `docs/writing/writers-room-collaboration-principles.md`
3. `docs/writing/episode-development-workflow.md`
4. `docs/writing/episode-artifact-naming-standard.md`
5. `docs/writing/github-usage-standard.md`
6. 当前上一集的 `FINAL.md` / `canon-propagation.md`
7. 当前开发集已有文件
8. 与该集有关的 Series Bible / World / Structure 权威文件

恢复后先回答：

- 项目现在做到哪里；
- 哪些已经 LOCK / FINAL；
- 当前真正未决的创意是什么；
- 下一步处于哪个 Gate；
- 哪些选择必须重新邀请编剧参与，而不能自行替她决定。

不要把 Git 历史当作当前状态；不要把聊天记忆当作唯一状态。

> **文件回答“现在是什么”；Git 回答“以前是什么”；Writers’ Room 原则回答“我们怎样一起继续写”。**

---

# 十六、最终协作句

以后任何时候如果流程与创作发生张力，优先记住：

> **工具服务作品，不反过来统治作品。**
>
> **前期结构不是为了把后期场景创作封死，而是为了让它在安全范围内继续生长。**
>
> **Assistant 负责把流程看牢；编剧始终留在“这场戏到底应该怎么活”的房间里。**
>
> **我先写，你来评；一场一场，把更好的东西一起撞出来。**
